# Requirements: console

File: `docs/requirements/console.md`. One block per rule. Questions go to `docs/requirements/QUESTIONS.md` with the rule ID.

Rule IDs are `CON-NNN`. An ID is never reused, even for a retired rule.

Status values:
- `observed` — the code does this today. Not yet confirmed as intended. No tests are written for it.
- `confirmed` — the human confirmed it is the intended behaviour. Tests required.
- `new` — comes from a ticket. Tests required.
- `retired` — no longer wanted. Tests for it are findings.

Only the human changes a status to `confirmed` or `retired`.

Fields used here (template fields plus the BA fields): status, statement, version, risk (high | medium | low), tickets, source, date, scope, tests, notes, history (one line per version change).
Scope of EXP1-R22C blocks: 1 = entry points, 2 = figures per ticket, 3 = difference column, 4 = errors and "no main session", 5 = JSON, D = decisions made in advance, O = out of scope.

### CON-011
- status: new
- statement: `python -m agent_console compare <KEY> <KEY> [--json]` prints the same comparison as the page; with no arguments `python -m agent_console` starts the server as today. Before comparing, the CLI refreshes the console's index so the comparison covers all logs. It first checks that its time zone, key patterns, console home and checkout are the ones the index was built with; if any differs, or the index does not record one of them, or has another schema version, it refuses: one clear line on stderr naming what differs or is missing (when some values differ and others are missing, the line saying the index was built with other values names all of them), exit code 2, nothing on stdout and nothing written to the index. A CLI run with another console home uses that home's own index and never touches the console's index. When the CLI's console home (the console's own or another) has no index file yet, there is nothing to check: the CLI builds a new index there, compares and exits with code 0. An index that cannot be opened or refreshed (locked, not a database, or the scan ends in an error), or any other error while the CLI scans or compares: one line on stderr naming the error class (no details, never a traceback), nothing on stdout, exit code 1; exit code 2 stays for usage, refusal and unknown key. An index path that is a symbolic link (dangling or not) is refused after the usage checks (CON-034) and before the index check: one line on stderr saying the index is a symbolic link, nothing on stdout, exit code 2, and no file created at the link or at its target. A refusal creates no file and changes no index data, in the CLI's home or anywhere else (no -wal or -shm file left beside an index that had none). The CLI never runs the git fetch of the claims data.

- statement: A failed run is a sub-agent run that did not complete: it ended in an API error, ended in a permission denial, failed before it started, or has no final reply. A spawn with no tool_result and no run file is not counted, so not failed either. Log markers: API error = an assistant record with isApiErrorMessage true (with error/apiErrorStatus), or a system record with subtype "api_error" (level "error"), as the last turn of the run; permission denial = a tool_result with is_error true whose text says the permission was denied ("Permission to use ... has been denied", "Permission for this action was denied ...", "The user doesn't want to proceed with this tool use"), and no final reply follows it in the run; a run that hits a denial and then sends a final reply completed and is not failed (the same last-turn rule as for API errors); final reply = the run's last assistant turn holds a SubagentHandback call (whatever else sits next to it), or holds no SubagentHandback call and has text and no tool_use at all (consecutive assistant records with the same message.id are one turn: Claude Code writes one API reply as several records); a last turn with no SubagentHandback call that has text next to another tool_use is not a final reply, whether the file ends on that open tool_use or on its tool_result: the run asked for a tool and did not finish; no final reply = neither, e.g. the last assistant turn is only a tool_use, text next to an ordinary tool_use, or the file ends on a tool_result that follows such a turn; a tool_result written after a turn that holds a SubagentHandback call (the handback's own result) does not take the final reply away when it is not an error; when that tool_result has is_error true (a denial or any other error), the handback did not go through and the run is failed. When the last assistant turn holds a SubagentHandback call next to other tool_uses, the results of those other tool_uses (in the same user record or in separate records, error or not, a denial included) do not make the run failed; only the handback's own result with is_error true does. A last turn with no SubagentHandback call is unchanged. A sub-agent run whose log file is gone (Claude Code deletes old logs; the index keeps its rows), or is missing or cannot be read when the comparison reads it, cannot be read for these markers: it counts as a run and is not failed.

### CON-022
- status: new
- statement: Wait time (main sessions only, summed over all the ticket's main sessions) is the sum of gaps from an assistant turn that stops for the person to the next gap end (see below). A stop for the person is a turn that ends with end_turn, with an AskUserQuestion call, or with a permission prompt, each only when the log shows it; a permission prompt that leaves no trace in the log is not counted. A gap starts at the timestamp of its stop record: the assistant record with the end_turn stop, or the assistant record that holds the AskUserQuestion tool_use or the tool_use whose permission prompt was rejected (not the time of the rejection or the dismissal). A gap ends at a gap end: a typed message, or the person's answer to an AskUserQuestion. A rejected permission prompt is a stop, not a gap end; its gap ends at the next typed message. A dismissed AskUserQuestion (its tool_result has is_error true) is not an answer: it counts as a rejected prompt, so its gap ends at the next typed message. Each gap end closes at most one gap, which starts at the latest stop after the previous gap end; earlier stops in the same stretch add nothing, so no interval is counted twice. A stop with no gap end after it (e.g. the session ends) adds nothing. Example: the person types at 0 s; the assistant stops with an AskUserQuestion at 10 s; the person answers at 310 s (gap 300 s); the assistant stops with end_turn at 400 s; a task notification wakes it and it stops again with end_turn at 500 s; the person types at 1100 s (gap 600 s, from the 500 s stop; the 400 s stop adds nothing). Wait time = 900 s. Example of a dismissed AskUserQuestion: the assistant stops with an AskUserQuestion at 10 s; the person dismisses it at 40 s (tool_result is_error true, "The user doesn't want to proceed with this tool use"), which ends no gap; the person types at 400 s (gap 390 s, from the 10 s stop). Wait time = 390 s. Text the person typed ends a gap, a slash command included. Task notifications, hook output, local command output, the "[Request interrupted by user]" marker, tool results other than an AskUserQuestion answer, peer messages and other machine-written user records do not end a gap. In older logs with no origin marker, a user record that is not a tool result and not one of those machine-written kinds counts as typed by the person. A gap under 60 s counts as zero; gaps over 2 hours count in full. Log markers: a typed message = a user record with origin.kind "human" (not isMeta, no toolUseResult, no tool_result block), or a user record with no origin marker (no origin field, or an origin that is not an object or has no kind), not isMeta, not isCompactSummary true and not isVisibleInTranscriptOnly true, whose text is a slash command ("<command-name>...") or plain text that is not local command output ("<local-command-...>") and not "[Request interrupted by user]"; task notifications have origin.kind "task-notification", peer messages "peer" (isMeta); a user record with isMeta true never ends a gap, whatever its origin; hook output is not a user record in the logs: it is an `attachment` record with attachment.type "hook_success" or a `system` record with subtype "stop_hook_summary", so it never ends a gap (a hook text written as an isMeta user record ends no gap either); an end_turn stop = an assistant record with message.stop_reason "end_turn" (other values, e.g. "tool_use" or "stop_sequence", are not an end_turn stop); an AskUserQuestion answer = the tool_result of that tool_use when it does not have is_error true (one with is_error true is a dismissed AskUserQuestion, see above); a rejected permission prompt = a tool_result with is_error true and the text "The user doesn't want to proceed with this tool use". A main session whose log file is gone, or is missing or cannot be read when the comparison reads it, adds no wait time (its other figures still come from the index). Wait time is found per main-session log file: a stop in one file is never closed by a gap end in another. A resumed session's file can repeat records of an earlier main session of the same ticket; each gap then counts once across the ticket's main sessions. Two gaps are the same gap when their stop records share a uuid or share message id + requestId (the same pair is the same API reply, as in the usage dedupe); only when a stop record has neither a uuid nor message id + requestId, by the pair (stop timestamp, gap end timestamp). Of gaps that are the same, the one with the earliest gap end counts. The match applies within one file too: two gaps in one file whose stop records share message id + requestId (one API reply) are one gap. Example in one file: the person types at 0 s; stop uA (end_turn, message id M1, requestId R1) at 100 s; the person types at 400 s (gap 300 s); stop uB (end_turn, the same M1 and R1, another uuid) at 500 s; the person types at 1100 s (gap 600 s, the same gap as the first). Wait time = 300 s, not 900 s. A copied stop that is closed only in the resumed file (the first file ends after it) is one gap, counted once. Example of a resumed session: file 1: the person types at 0 s; the assistant stops with end_turn at 100 s; the person types at 400 s (gap 300 s); the assistant stops with end_turn at 500 s; file 1 ends. File 2 (the resume) repeats all of file 1's records (same uuids), then the person types at 2000 s (gap 1500 s, from the 500 s stop). Per file: file 1 = 300 s, file 2 = 300 s + 1500 s; the 100 s stop's gap is the same in both and counts once. Wait time = 1800 s, not 2100 s. Edge cases: message id + requestId is a match key only when the stop record has both; the (stop timestamp, gap end timestamp) pair matches only two stops that both have no uuid and no message id + requestId pair. A user record with no origin marker whose text starts with "<task-notification" is a task notification and ends no gap. A compact summary (the user record Claude Code writes after a context compaction: isCompactSummary true, also isVisibleInTranscriptOnly true, no origin, not isMeta) is machine-written and ends no gap; a user record with no origin marker and isVisibleInTranscriptOnly true ends no gap either. These two flags are checked only for user records with no origin marker: a user record with origin.kind "human" stays a typed message whatever these flags say. A gap end with no timestamp still closes its stop but adds no gap; a stop with no timestamp adds no gap either.
